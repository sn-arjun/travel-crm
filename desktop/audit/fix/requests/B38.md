# B38 backend requests (desktop could not fix these)

Evidence: first story recording, `desktop/showcase/.work/story-take1/sheets/s03.png` and `s05.png`, plus the seeded demo tenant (Sahyadri Holidays).

## 1. Numbering prefixes are not applied to invoice numbers
- Settings > Numbering lets a tenant set a prefix (the demo uses `SH-INV`), but new invoices, credit notes and proforma invoices still get the default `INV-2026-27-0027`, `CN-2026-27-0001`, `PI-2026-27-0002` (invoice list in s03.png).
- Needed: the invoice, credit-note, debit-note and proforma number generators read the tenant's numbering settings (prefix, financial-year token, padding). The desktop only displays `invoiceNumber` as returned.

## 2. Trip passenger phone is not normalised server-side
- Before B38 the trip form posted `9820144562` (the country code was lost). The desktop now posts E.164 (`+919820144562`) for new and edited trips and reads legacy digit-only values correctly, but rows already stored (and any API client) can still send bare digits.
- Needed: `POST/PUT /fleet/trips` normalise `passengerPhone` to E.164 (default country +91 for 10-digit numbers), and a one-off migration for existing rows. The same applies to `POST/PUT /fleet/drivers` (`phone`, `emergencyContactPhone`): the driver forms still send bare national digits because the driver app signs in by phone and its matching rules live in the backend.

## 3. `POST /auth/login` returns no tenant object
- The login response has `user` but no `tenant`, so the desktop auth store has `tenant: null`. B38 works around it by reading the company profile from `GET /settings/company` (cached in `useCompanyProfile`), so templates resolve `{{company_name}}`, `{{company_phone}}` and `{{company_email}}`.
- Needed (optional clean-up): return `tenant: { id, name, ... }` from login and refresh so other screens can show the company name without an extra request.

## 4. Lead activity metadata
- `GET /leads/:id/activities` returns `metadata` as a JSON string for `status_change` rows (`old_status`, `new_status`, `lost_reason`). The desktop parses it to show "Status changed from Contacted to Qualified". Returning it as an object (camelCase) would remove the parsing; not blocking.
